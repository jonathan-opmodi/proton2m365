# Maintainers

## Sign-in

proton2m365 ships no sign-in app and no client ID: every user registers their own (docs/setup-own-app.md). Keep
it that way; a shared public client ID with mail permissions would need a dedicated tenant, abuse monitoring and
a rotation plan. Never commit a real client or tenant ID (scripts/check-publish.sh refuses the maintainer's).

## Releasing

1. `scripts/check-publish.sh` passes; CI is green on macOS, Linux and Windows.
2. Tag `vX.Y.ZrcN` → the publish workflow builds, checks the version matches the tag, uploads to TestPyPI and
   attaches the wheel to a GitHub pre-release. Testers install that wheel (`pipx install ./proton2m365-...whl`)
   so dependencies come from PyPI only.
3. Tag `vX.Y.Z` → PyPI. Afterwards: `pipx install proton2m365`, `proton2m365 --help` and `scan` on a test
   export.

## Homebrew

Each release (not release candidates) attaches `proton2m365.rb` to the GitHub release, generated by
`scripts/make-homebrew-formula.py` from `uv.lock` and the PyPI source archive. Copy it into the tap repository
(`homebrew-proton2m365`, `Formula/proton2m365.rb`) and run `brew install --build-from-source` and `brew test` on
it before pushing; users then `brew install jonathan-opmodi/proton2m365/proton2m365`. The README mentions brew only once
the tap exists.
